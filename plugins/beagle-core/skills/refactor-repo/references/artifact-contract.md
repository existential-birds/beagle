# Artifact Contract

The helper uses JSON, UTF-8, schema version 1. All paths are explicit CLI arguments.
Use `write_file` to author campaign inputs and `read_file` to inspect outputs.
The examples below are illustrative schema data, not findings about a real repository.

## Source artifacts

- `snapshot`: generated by the helper with repository, chosen ref, commit SHA, timestamp, existing label names, and all-state issue/PR records.
- `inventory`: generated by the helper with commit SHA, included blob metadata, components, and exclusion reasons.
- The snapshot is complete only after every GitHub page has succeeded; failed calls must not be represented as an empty backlog.
- Both artifacts and the proposal ledger must refer to the same SHA.
- Use full immutable SHAs for evidence, not branch-relative links.
- Inventory does not include dirty/untracked changes, and does not read credential file content.

## Coverage input

```json
{
  "sha": "FULL_COMMIT_SHA",
  "triaged": ["src/pricing.py", "tests/test_pricing.py"],
  "read": ["src/pricing.py", "tests/test_pricing.py"],
  "skipped": [{"path": "docs/old-notes.md", "reason": "Historical notes, outside executable analysis."}],
  "crosscut_review": "Describe which shared contracts, callers, and shard overlaps were checked."
}
```

- `triaged`: unique included paths whose role and relevance have been assessed; not a claim of line-by-line reading.
- `read`: unique subset of triaged paths read deeply enough for semantic evidence.
- `skipped`: included paths intentionally omitted, each with a substantive reason.
- Triaged and skipped paths are disjoint and together must equal every included inventory path.
- Pre-inventory exclusions remain in the inventory's separate exclusion report.
- `crosscut_review` records actual analysis, not merely an intended future pass.
- Evidence must cite an included path listed in `read`.
- The validator checks consistency, not whether the claimed reading really occurred; the adjudicator verifies tool receipts.
- Do not stuff every path into `read` simply to make validation pass.

## Proposal ledger

```json
{
  "repo": "OWNER/REPO",
  "sha": "FULL_COMMIT_SHA",
  "candidates": [
    {
      "id": "billing-rounding-policy",
      "title": "Centralize the shared invoice rounding policy",
      "decision": "accepted",
      "confidence": "high",
      "problem": "Explain the exact structural obstacle at the cited locations.",
      "change_cost": "Explain the observed duplicated edits or comprehension burden.",
      "evidence": [
        {"path": "src/pricing.py", "start": 10, "end": 30, "symbol": "invoice_total", "note": "State what these lines demonstrate."}
      ],
      "smells": ["Duplicated Code"],
      "refactorings": [{"name": "Extract Function", "chapter": 6}],
      "steps": ["Add characterization tests for both existing callers.", "Extract the shared calculation and migrate one caller at a time, testing each."],
      "invariants": ["Rounding order, currency units, exceptions, and public signatures remain unchanged."],
      "tests": ["Name existing test files and required boundary cases; give only commands discovered in the repo."],
      "acceptance": ["Both callers use one policy implementation and their behavior tests pass."],
      "non_goals": ["No new pricing behavior or unrelated module reorganization."],
      "risks": ["Confirm the two callers do not intentionally implement different rounding contracts."],
      "alternatives": ["Keep separate implementations if their ownership or contracts require independent evolution."],
      "priority": "medium",
      "effort": "small",
      "ranking_reason": "Explain recurring change cost and the bounded affected surface.",
      "review": "Record the verification pass and evidence that addressed potential false positives.",
      "duplicate_check": {"status": "clear", "rationale": "Record search terms, closest issues/PRs, and why this root cause is not covered."},
      "validation": {"status": "not-run", "detail": "Proposal-only analysis; implementation tests have not been executed."},
      "labels": [],
      "assignees": []
    }
  ]
}
```

## Field rules

- `id`: stable lowercase-hyphenated root-cause/ownership key; unique within the ledger. `manifest` is reserved for campaign metadata.
- Do not include scan date, line number, commit SHA, or a generated sequence number in that key.
- Same root cause in another run should reuse the key; unrelated problems must not share it.
- `decision`: accepted, rejected, duplicate, or needs-evidence.
- Non-accepted entries only require id, decision, and a nonempty `reason`; preserve their detailed evidence if useful.
- An empty candidates array is valid and produces a zero-draft manifest.
- Accepted entries require all fields in the example and high confidence.
- `smells`: exact meaningful names from Fowler, selected by the analyst rather than a metric scanner.
- `refactorings`: named catalog techniques with their chapter in 6–12; the reviewer checks name/chapter correspondence.
- `steps`, `invariants`, `tests`, `acceptance`, `non_goals`, `risks`, and `alternatives`: nonempty string arrays.
- `evidence`: nonempty array of included paths, positive ordered line ranges, symbol names, and explanatory notes.
- The helper validates ranges structurally, not against actual line count; reread each cited range before approval.
- `priority`: high, medium, low; `effort`: small, medium, large. These do not invent GitHub labels.
- `labels`: existing exact repository label names only; empty is valid when repository policy permits it.
- `assignees`: real GitHub logins without an `@` prefix; use an empty array to explicitly leave unassigned.
- `duplicate_check.status` must be clear for accepted entries. A fingerprint match or title collision still blocks preparation.
- `validation.status`: not-run, passed, failed, unavailable. Detail must state what actually ran or why it did not.
- Never label planned tests as passed or imply that the proposed refactoring has been implemented.

## Prepared outputs

- Use a new or empty output directory; preparation refuses to overwrite previous drafts and publication journals.
- `<id>.md`: readable issue body, with source permalinks and a stable hidden marker.
- `<id>.json`: exact repository, ref, SHA, id, and issue payload containing explicit title, body, labels, and assignees.
- `manifest.json`: source identity, coverage totals, decision counts, and the authoritative list of draft IDs.
- Publish only IDs in that manifest; never glob a directory and accidentally feed `manifest.json` or a journal as an issue.
- A digest marker is derived from repository and stable key, not current wording or SHA.
- Preparation validates all candidates before writing any drafts, apart from ordinary filesystem failure during output.

## Publication journal

- `<id>.journal.json` is written before the first POST and retained beside its draft.
- `pending`: creation was about to be attempted; the result may be unknown.
- `created-unverified`: API returned a number, but exact-target verification is not yet complete.
- `verified-created`: this attempt created an issue whose fields were read back successfully.
- `verified-existing`: a stable-marker match was read back and matched the exact draft; no second POST was sent.
- A verified-existing issue may have been created by an earlier attempt; do not count it as a new creation.
- A pending journal with no visible match is unresolved, not evidence that POST failed before reaching GitHub.
- Closed or edited matching issues require deliberate reconciliation; the helper never reopens or overwrites them.

## Portability and limitations

- Python stdlib only; Git and `gh` are external prerequisites.
- GitHub.com only for this helper; enterprise hosts require explicit adaptation and tests, not an inferred hostname.
- Default metadata includes common source, schema, config, test, and documentation extensions; exclusions are heuristic.
- No semantic smell detector, AST engine, issue-quality judge, or performance profiler is embedded in the script.
- The agent performs analysis, grounded adjudication, and semantic duplicate checks; the helper handles reproducible mechanics.
